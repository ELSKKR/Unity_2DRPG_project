# 系統 1 — 場景架構

## 這個系統在解決什麼

Unity 的「場景」(Scene) 可以想成一個**舞台**。直覺的做法是：村莊是一個舞台、房子內部是另一個舞台，玩家走進門就換台。

問題出在——**換舞台時，舞台上的東西會被全部清掉重來**。玩家角色、攝影機、背包裡的道具、任務進度，全部歸零。專案最早的版本就是這樣，走進房子會發現背包空了、任務不見了、玩家角色重新出現在地圖原點。

## 第一次嘗試：DontDestroyOnLoad

Unity 內建一個叫 `DontDestroyOnLoad` 的功能，可以標記某個物件「換場景時不要銷毀我」。乍看之下剛好解決問題，專案裡也確實留了一支 `PersistAcrossScenes.cs` 就是幹這個的。

但實務上它很難維護：

- **每個要保留的物件都得記得標記**。漏掉一個，症狀是「某個功能莫名其妙失效」，而且不會報錯——很難查。
- **被標記的物件會脫離所有場景**，在 Unity 編輯器的階層視窗裡跑到一個獨立區塊，變成一坨孤兒清單，不好找也不好調整參數。
- **回標題畫面時要手動一個個銷毀**，同樣容易漏。

換句話說，它能動，但它把維護成本轉嫁到「人要記得」上面。

## 最後定案：常駐場景 ＋ 加法式載入

改成兩層結構：

**下層 `Persistent.unity`** — 永遠載入、永不卸載。裡面放：
- 玩家角色
- 攝影機
- 所有管理器（存檔、任務、背包、對話、情報、世界狀態、音效）
- 整個 UI 畫布（對話框、選單、通知）

**上層關卡場景** — `Forest_Village`（村莊）、`House_Interior_A~D`（四間室內）、`TitleScreen`（標題畫面）。這些用**加法式載入**(Additive Loading) 疊在 Persistent 上面。所謂加法式，就是「載入新場景但不清掉舊的」，兩層同時存在。進出房子時只卸載上面這一層，下層動都不動。

兩種做法的對照：

| | DontDestroyOnLoad | 常駐場景 |
|---|---|---|
| 常駐物件在哪 | 散在各處，靠標記 | 集中在一個場景檔 |
| 編輯器內能不能調 | 執行時才存在，很難 | 直接打開就能編輯 |
| 會不會漏標記 | 會，且不報錯 | 不存在這個問題 |
| 重置遊戲 | 手動逐一銷毀 | 卸載上層即可 |

## 轉場的實際流程

負責的是 `SceneTransitionManager.cs`。玩家在門口按互動鍵後，它依序做七件事：

1. **鎖住玩家輸入** — 不然轉場動畫播到一半玩家還能走，會走到奇怪的位置
2. **打開黑幕的滑鼠攔截**（見下面的坑）
3. 畫面淡出（0.4 秒）
4. 卸載目前的關卡場景
5. 加法式載入目標關卡場景
6. **把玩家搬到目標場景指定的「出生點」**（`PlayerSpawnPoint`，每個場景自己放，用字串 ID 對應）
7. 執行呼叫端的收尾工作 → 畫面淡入 → 解鎖輸入

第 6 步的設計有個細節：出生點 ID 可以**傳空值**。讀檔時就是傳空的——因為讀檔要用的是存檔裡記錄的精確座標，不是門邊的出生點。這個彈性讓同一套轉場流程可以同時服務「走進門」和「讀檔進遊戲」兩種完全不同的需求。

## 踩過的坑（三個）

### 坑一：全螢幕黑幕吃掉所有滑鼠點擊

轉場用的那張黑色圖片平常是完全透明的，大家會忘記它還在。但 Unity 的 UI 圖片有個預設開啟的屬性叫 `raycastTarget`（是否攔截滑鼠事件）——**看不見歸看不見，滑鼠點擊全部被它吃掉**。

症狀是：標題畫面的按鈕點不動，但看起來一切正常。

修法是只在轉場那 0.8 秒把攔截打開，轉場結束立刻關掉。

### 坑二：場景名稱打錯字 → 玩家永久卡在黑畫面

Unity 的 `LoadSceneAsync` 在找不到場景時（名稱打錯、或忘記把場景加進建置清單）會回傳 `null`，**不會拋出錯誤**。原本的程式碼直接往下用這個 null，結果是：畫面已經黑了、舊場景已經卸載了，然後程式在這裡崩潰——玩家看到的是一片全黑，動不了，也沒有任何錯誤提示。

修法是加一段救援邏輯：偵測到 null 就印出明確的錯誤訊息（告訴開發者要檢查名稱和建置清單），**並把剛剛卸載掉的舊場景載回來**，讓玩家至少能繼續玩，而不是卡死。

### 坑三：採收過的作物會復活

進出房子之後，採收過的作物整片重新長回來。

原因是：採收的動作只是把地圖圖塊清空，那是**執行期的暫時狀態**；場景重新載入時，Unity 會用場景檔裡的原始資料整個蓋回去——而場景檔裡那些作物當然還在。

修法是加一個 `WorldStateManager` 記住「哪些格子已經被採過」，場景載入完成後照著記錄再清空一次。同樣的模式後來也用在「撿過的道具不會重新出現」上。

**這個坑的通則是**：任何「玩家改變了世界」的事情，都不能只改執行期狀態，必須另外記錄下來，否則場景一重載就打回原形。這條規則直接催生了系統 4。

## 開機流程

`BootstrapLoader.cs` 負責。遊戲啟動時 Persistent 場景先起來，它做兩件事：

1. **把玩家角色關掉** — 標題畫面不需要玩家角色，而且它得等到「開始遊戲」時才知道該出現在哪
2. 加法式載入標題畫面

玩家角色要等到按下「新遊戲」或「讀取存檔」時，才由存檔系統打開並定位。這個「先關掉、之後才打開」的設計後來造成一個隱蔽的 bug——見系統 4。

## 報告可以這樣講

賣點是「**一個看似簡單的需求，為什麼直覺解法不夠用**」。DontDestroyOnLoad 是很好的對比材料：不是它不能動，而是它把維護成本轉嫁給人的記憶力，而常駐場景把這個成本直接消滅。

三個坑各有不同的教學價值：
- 坑一是「**看不見不代表不存在**」——透明的 UI 元件依然會攔截事件
- 坑二是「**錯誤處理不是為了正常流程，是為了失敗時不要死得太難看**」
- 坑三是「**執行期狀態 vs 持久化狀態**」的分野，這是整個存檔系統的思想起點

# 系統 2 — 對話與任務系統

這是整個專案最核心、也最複雜的系統。花的時間最多，改版次數也最多。

## 這個系統在解決什麼

一個 RPG 的 NPC 要能做到：

- 玩家還沒接任務時，說一套委託的話，並且給選項讓玩家決定接不接
- 玩家接了任務但還沒完成時，說一套催促的話
- 玩家帶著東西回來時，說一套收下的話，並且真的完成任務、扣道具、發獎勵
- 任務結束後，說一套閒聊的話
- 而且這一切要能**串成好幾個階段**（賽勒：先找配方 → 再採作物）

如果把這些寫死在程式裡，每加一個 NPC 就要新增一支腳本、每改一句台詞就要重新編譯。三個 NPC 還撐得住，三十個就不可能了。

## 核心設計：資料驅動

「資料驅動」(Data-Driven) 的意思是：**程式只寫「怎麼判斷該說哪段話」，至於話的內容、任務的條件、獎勵是什麼，全部放在編輯器裡可以填的資料檔案裡。**

Unity 提供的工具叫 `ScriptableObject` — 可以想成「一個可以在專案裡當檔案存起來的資料表格」。它不是場景裡的物件，就是一份純資料，可以在編輯器裡填、可以被多個地方共用。

專案裡的資料檔分三層：

```
NPCConversationData（一個 NPC 的完整對話任務資料，一個 .asset 檔）
├── speakerName          角色顯示名稱
├── stages[]             任務階段陣列 ← 核心
│   └── NPCQuestStage    每個階段
│       ├── quest                對應哪條任務（指向 QuestData）
│       ├── canAcceptQuest       這個 NPC 能不能發這條任務
│       ├── completesQuestOnHandIn 玩家帶東西來能不能在這裡交
│       ├── 解鎖條件（四種，見下）
│       ├── turnInItems[]        要交什麼道具、各幾個
│       ├── rewardItem           交完發什麼獎勵
│       ├── unlockEventID        完成時標記什麼世界事件
│       └── 四段對話：intro / reminder / handIn / completed
└── chats[]              沒有任何階段解鎖時的閒聊
```

早期版本是「一段對話就要拆成一個獨立的 .asset 檔」，一個 NPC 會散成七八個檔案，改一句話要在專案裡翻半天。後來整併成「一個 NPC 一個檔」，維護體驗差很多。

## 四狀態機

程式端的核心邏輯就一件事：**現在該播哪一段？**

`NPCDialog.cs` 每次玩家互動時做兩步判斷。

**第一步：找出「目前該互動的階段」**（`GetActiveStage`）

從第一階段開始往後走，遇到下面任一情況就停下來：
- 這一階段的**解鎖條件還沒滿足** → 停在上一個已解鎖的階段
- 這一階段**還沒完成** → 就是它了

**第二步：判斷這個階段目前是什麼狀態**（`EvaluateStageState`）

| 狀態 | 判斷條件 | 播哪段 | NPC 頭上顯示 |
|---|---|---|---|
| `CanAccept` | 任務還沒接，且這個 NPC 可以發任務 | `intro` | 黃色「！」 |
| `InProgress` | 任務已接，但要交的道具還不夠 | `reminder` | 無 |
| `CanHandIn` | 任務已接，道具也夠了 | `handIn` | 橘色「！」 |
| `Completed` | 任務已完成 | `completed` | 無 |

四種狀態各對應一段可以自由填寫的台詞，這就是為什麼加一個 NPC 完全不用寫程式——填資料就好。

## 解鎖條件有四種

每個階段可以設定要滿足什麼才會解鎖：

| 條件 | 意思 | 用途舉例 |
|---|---|---|
| `requiredCompletedQuest` | 要先完成某條任務 | 賽勒的第二階段要先完成第一階段 |
| `requiredAcceptedQuest` | 要先**接下**某條任務（不用完成） | 委託人不會主動提起，要等玩家先跟別人談過 |
| `requiredItem` | 要持有某個道具 | 拿著信物才會有反應 |
| `requiredEventID` | 要某個世界事件已觸發 | 看過某段演出之後 |

這四種是逐步加上去的——每次遇到「這個劇本寫不出來」就補一種。四種湊齊之後，目前所有劇情需求都表達得出來。

## 一個關鍵設計：同一條任務可以掛在兩個 NPC 身上

`canAcceptQuest` 和 `completesQuestOnHandIn` 這兩個開關拆開，是為了支援「**A 發任務、B 收東西**」的結構：

- 發任務的人：`canAcceptQuest = true`、`completesQuestOnHandIn = false`
- 收東西的人：`canAcceptQuest = false`、`completesQuestOnHandIn = true`

如果把兩件事綁在一起，就只能做「誰發的任務就找誰交」，跑腿類的劇情全部寫不出來。

## 對話選項的副作用系統

選項 (`DialogChoice`) 除了顯示文字和反應台詞，還可以掛五種副作用：

| 欄位 | 效果 |
|---|---|
| `acceptsQuest` | 選了就接下任務 |
| `completesHandIn` | 選了才算真的完成交付 |
| `markEventID` | 選了就標記一個世界事件旗標 |
| `grantsIntel` | 選了就解鎖一則情報 |
| `requiredIntel` | 要先解鎖某則情報，這個選項才能選 |

`completesHandIn` 是為了亞爾的佩劍支線加的——玩家撿到劍之後可以選擇「還給他」或「留著自用」，兩種都要有結局，所以交付不能是「進到這段對話就自動完成」。

## 改版一：選項的副作用時機不對

`markEventID` 和 `grantsIntel` 一開始寫在「玩家按下選項的那一刻」。

結果是：玩家選了「聽愛拉說你把劍弄丟了？」，**反應台詞都還沒播完**，右上角就跳出「獲得情報」的通知。而任務的通知是整段對話結束才跳的——兩個時機不一致，看起來很雜亂。

修法是加一個 `pendingChoice` 欄位記住「玩家選了哪個」，實際的標記/解鎖動作延後到對話真正結束 (`EndDialog`) 才執行。這樣所有通知的時機就一致了。

**這個修改的通則是**：副作用的「觸發點」和「生效點」可以分開。記住意圖、延後執行，是讓多個系統時序一致的常用手法。

## 改版二：多階段 NPC 要講兩次話（最後一個修的 bug）

賽勒交完配方後，玩家得**連續對話兩次**才拿得到下一個任務。

**成因是架構天生的**：一次互動只播一段對話。完成任務的動作掛在「對話結束」的回呼上，所以「解鎖下一階段」必然發生在對話結束**之後**——這時玩家已經跳出對話了，要等下次互動才會看到新階段。

而讓它「看起來像壞掉」的是**台詞重複**：第一階段的收下台詞已經把配方比例和委託內容講完了，第二階段的委託台詞又講一次同樣的比例。玩家的體感是「他剛剛不是講過了嗎，怎麼要聽兩次才算數」。

修法分兩層：

**程式層** — 新增 `TryChainNextStage()`：完成一個階段後重新判斷一次，如果換到了新階段而且狀態是「可接取」，就直接把下一段委託接著播完，整串變成**一次連續對話**。

這裡有個安全性問題要先確認：能不能在「對話結束」的回呼裡再開一段新對話？答案是可以——因為 `EndDialog()` 是**先關面板、把所有狀態清空之後**才呼叫回呼的，所以新對話拿到的是乾淨狀態。這點是動手前先讀程式碼確認的，不是試出來的。

**內容層** — 把重複的兩句從第一階段搬到第二階段。而且是**逐字沿用**、不重寫，因為這樣不會引入新字元，就不用重跑字型烘焙流程（見系統 9）。

## 報告可以這樣講

這章是整個專案的架構核心，適合當技術部分的第一章。三個層次的賣點：

1. **資料驅動的價值**：用「加一個 NPC 要不要寫程式」當對照，最容易讓非技術聽眾理解為什麼要多花這個功夫
2. **四狀態機**：可以畫成一張狀態轉移圖，是很好的視覺化素材
3. **兩次改版**：一個是時序問題（副作用延後生效），一個是體感問題（明明沒壞但玩家覺得壞了）。後者特別值得講——**它在技術上完全正確，是「內容」和「架構」的接縫處出了問題**，這種 bug 只有實際玩過才抓得到

# 系統 3 — 情報系統

## 這個系統在解決什麼

原本的問題很具體：**亞爾的佩劍支線，玩家憑什麼知道他弄丟了劍？**

最早的版本是玩家一走近亞爾，選項裡就直接出現「聽說你在森林弄丟了佩劍？」——但玩家根本還沒跟任何人聊過，這句話從哪來的？角色像會讀心術。

要解決這個，需要一個「玩家知道什麼」的概念。這就是情報系統。

## 架構：完全比照任務系統

情報系統的架構是刻意「抄」任務系統的，三個檔案一一對應：

| 任務系統 | 情報系統 | 做什麼 |
|---|---|---|
| `QuestData` | `IntelData` | 一則資料（ID、標題、內文） |
| `QuestManager` | `IntelManager` | 已解鎖清單 + 事件 + 存讀檔 |
| `QuestUI` | `IntelUI` | 面板（清單 + 詳情） |

**為什麼刻意抄**：任務系統已經被驗證可行、跟存檔也接好了，照同一個模子做，接存檔、接通知、接 UI 全部都是熟路，開發速度快很多，而且未來維護的人只要懂一套就懂兩套。

UI 面板也是直接複製任務面板整包再改造——刪掉「目標」區塊（情報沒有這個概念）、把說明區往上補位置填滿空間。省下重新排版的功夫。

## 怎麼接進對話系統

在對話選項上加兩個欄位：

- `grantsIntel`：選了這個選項就解鎖這則情報
- `requiredIntel`：沒解鎖這則情報，這個選項就是「鎖住」的

於是流程變成：跟愛拉聊天 → 她提到亞爾弄丟劍的事 → 解鎖情報「亞爾暴躁的原因」 → 現在去找亞爾，那個選項才選得動。

## 最重要的設計決策：鎖住的選項要「藏起來」還是「看得到選不到」？

第一版是**直接把選項濾掉**——沒解鎖情報就不顯示。

但這樣有個問題：玩家完全不知道這裡有東西。他跟亞爾講完話，看到兩個選項，選完就走了，永遠不知道自己錯過了一整條支線。

改成第二版：**選項照樣顯示，但文字變成「？？？」，顏色變半透明**。玩家看得到「這裡有第三個選項」，選下去會跳出提示：

> 缺少情報「？？？」，或許該先打聽點消息。

這個改動的效果是把「錯過」變成「好奇」。玩家知道有東西沒拿到，會主動去找人聊天。

### 兩個追加的細節

**一、提示裡故意不寫情報名稱。** 第一版的提示是「缺少情報『亞爾暴躁的原因』」——講出名字就等於先暴雷了，玩家還沒打聽就已經知道答案。改成一律顯示「？？？」，只讓玩家知道「這裡缺一則情報」，具體是什麼要自己去問。

**二、選到鎖住的選項不會結束對話。** 跳完提示就停在原地，玩家可以繼續選別的選項。如果每選錯一次就要重新開啟對話，會很煩。

## 一個順手修掉的隱藏 bug

第一版「把選項濾掉」的做法，其實藏著一個還沒被觸發的 bug。

程式在判斷「玩家選的是哪個選項」時，是用**索引**（第 0 個、第 1 個…）去查資料的。但如果顯示時濾掉了某些選項，畫面上的第 1 個可能是資料裡的第 2 個——**兩邊指的不是同一個東西**。

這個 bug 當時沒被發現，純粹是運氣：亞爾那個鎖住的選項剛好是**最後一個**，濾掉最後一個不會影響前面的索引。如果哪天有人把鎖住的選項放在中間，玩家選了 A 卻觸發 B 的效果，而且會極難查。

改成「不過濾、只是顯示成？？？」之後，畫面上的順序和資料裡的順序**永遠是同一份陣列**，這個問題從根本上消失了。

**這個案例的教學價值**：一個為了體驗做的改動，順手消滅了一個結構性風險。有時候「比較好的設計」和「比較安全的實作」會指向同一個方向。

## 情報鏈的內容設計

做完機制之後才發現一個內容層面的限制：**一個 NPC 的委託對話 (`intro`) 一輩子只能給玩家一個分支**——因為選了接任務的選項之後，這段對話就永遠不會再播了。

那「一個 NPC 給兩則情報」怎麼辦？

解法是利用「不接任務的選項」：愛拉的委託對話有三個選項，前兩個會接任務，第三個「村口那位先生是誰？」**故意不接任務**。所以問完之後這段對話會重播，玩家可以再選前兩個。天然做到「一次對話一則情報」。

另外，亞爾的話題**同一段內容複製在三個地方**（委託、催促、完成後閒聊）。這是刻意的冗餘，不是複製貼上偷懶——確保玩家不管在什麼進度都問得到，不會因為先接了別的任務就永久卡死在那個「？？？」上。

## 報告可以這樣講

這章的特色是**它講的是設計決策，不是程式技巧**，跟其他章形成對比，簡報節奏上很好用。

核心那一頁可以做成 A/B 對照：左邊「藏起來」、右邊「顯示？？？」，然後問聽眾「哪個玩家比較可能發現這條支線」。答案很直覺，但背後的道理（把錯過轉成好奇）值得講。

那個隱藏 bug 適合當收尾，說明「設計改善順帶消滅了技術債」。

# 系統 4 — 存檔與世界狀態

## 這個系統在解決什麼

兩個層次的問題：

**第一層（明顯的）**：關掉遊戲再打開，進度要還在——玩家在哪、背包有什麼、任務進行到哪。

**第二層（隱蔽的）**：**同一次遊玩之內**，世界的改變也要記得住。這就是系統 1 那個「作物會復活」的坑——進出房子會讓村莊場景整個重載，所有「玩家改變過的東西」都會被場景檔的原始資料蓋回去。

第二層才是真正麻煩的部分，而且它必須先解決，第一層才有東西可存。

## 世界狀態管理器

`WorldStateManager` 記三種東西，全部都是字串集合：

| 欄位 | 記什麼 | 用途 |
|---|---|---|
| `collectedItemIDs` | 撿過的道具（每個拾取物有唯一 ID） | 撿走的東西不會重新出現 |
| `eventFlags` | 一次性世界事件旗標 | 演出只播一次、對話解鎖條件 |
| `harvestedCropCells` | 採收過的作物格子 | 採過的地不會重新長 |

拾取物的唯一 ID 是用 `System.Guid.NewGuid()` 產生的亂數字串，在編輯器裡按右鍵就能生成一組。用亂數而不是手動編號，是因為手動編號一定會撞號，而撞號的症狀是「撿了 A 之後 B 也消失了」，非常難查。

`MarkEvent()` 有個小設計：它**回傳這次是不是第一次標記**。這樣「演出只播一次」就變成一行判斷，不用另外查一次。

## 存檔的資料結構

`SaveData` 是一個純資料類別，用 Unity 內建的 `JsonUtility` 直接序列化成一個 `.json` 檔：

```
sceneName            玩家在哪個場景
playerX / playerY    精確座標
quests[]             每條任務的 ID、狀態、階段
inventory[]          每格背包的道具 ID、數量
collectedItemIDs[]   ┐
eventFlags[]         ├ 世界狀態三件套
harvestedCropCells[] ┘
unlockedIntelIDs[]   已解鎖的情報
savedAtUtc           存檔時間（給存檔槽選單顯示）
totalPlaytimeSeconds 累積遊玩時數
```

檔案放在 `Application.persistentDataPath`，那是作業系統給每個應用程式的使用者資料夾。**不能放在專案的 Assets 底下**——打包成執行檔之後那個資料夾是唯讀的，寫不進去。

## 核心難題：存「參照」還是存「ID」？

這是存檔系統最關鍵的設計決定。

遊戲執行時，一條任務在記憶體裡是一個「指向 QuestData 資產的參照」。但**參照沒辦法存進 JSON** — 它只是一個記憶體位址，下次開遊戲就無效了。

所以存檔時要把參照換成**字串 ID**（`questID`、`itemID`、`intelID`），讀檔時再反查回來。

問題是：怎麼從 ID 查回資產？Unity 有個 `AssetDatabase` 可以做這件事，但**它只在編輯器裡能用，打包後不存在**。編輯器裡測試一切正常，玩家拿到的版本一讀檔就整個崩掉——這是典型的「只在編輯器裡對」的陷阱。

解法是 `GameDatabase`：一份手動維護的清單資產，裡面拖著全部的道具、任務、情報。讀檔時就在這份清單裡線性搜尋。

代價是**新增道具/任務/情報時，一定要記得把它拖進這份清單**。忘了的話存檔讀回來會少東西。所以三個 `ImportSave` 都加了明確的警告訊息：

> 存檔裡的任務 ID「xxx」在 GameDatabase 裡找不到對應資產，這條任務進度會遺失

不加警告的話，症狀是「玩家的某個任務莫名其妙消失」，沒有任何線索。

## 存檔的三個時機

1. **進出場景時**（走進門、走出門）
2. **從設定選單選「儲存並回到標題」時**
3. **開始新遊戲的當下** — 這個容易被忽略：如果不立刻存一次，玩家開了新遊戲馬上關掉，存檔槽還是顯示「空的」，他會以為遊戲沒記錄到

第 1 點有個細節：存檔是在**轉場完成後**才做的，不是按下門的當下。這樣存檔裡記的場景和座標才是門的另一邊，而不是門這一側。否則讀檔會出現在門外，感覺像沒進去過。

## 踩過的坑：讀檔時玩家角色是關閉的

這個 bug 很隱蔽。

開機流程會**先把玩家角色關掉**（系統 1 講過）。而 Unity 用來尋找場景物件的函式 `FindFirstObjectByType`，**預設會跳過關閉狀態的物件**。

結果是：讀檔時要把玩家搬到存檔座標，但那個當下玩家還是關閉狀態，所以「找玩家」這一步找不到人——而且**不會報錯，也不會有警告**，就是安靜地跳過定位。玩家會出現在地圖原點 (0,0)，通常是地圖外面。

修法是明確傳入 `FindObjectsInactive.Include` 參數，告訴它「連關閉的也要找」。

**這個坑的教學價值很高**：它示範了「安靜失敗」(silent failure) 有多可怕。程式沒崩、沒有紅字、日誌乾淨，但行為是錯的。

## 遊玩時數的計算

存檔槽選單要顯示「已遊玩 2 小時 14 分」，做法是兩個變數相加：

- `playtimeBaseSeconds`：讀檔當下，存檔裡原本就有的秒數
- `sessionElapsedSeconds`：這次讀檔以來累積的秒數

存檔時把兩個相加寫回去。

有個刻意的簡化：**開著背包/任務/設定選單也照樣計時**，不特別做暫停判斷。因為多數 JRPG 的「遊玩時數」就是這個存檔開著遊戲的總時間，為了選單另外繞一層邏輯不划算。

## 報告可以這樣講

這章最有料的是**「存參照 vs 存 ID」**這個決定，以及背後那個 `AssetDatabase` 陷阱。它是一個典型的「編輯器裡對、打包後錯」問題，而這類問題正是遊戲開發最容易翻車的地方（系統 9 還有一個更嚴重的）。

「安靜失敗」那個坑也很值得講——可以問聽眾：一個程式沒有報錯，是不是就代表它是對的？

# 系統 5 — UI 框架

## 這個系統在解決什麼

專案裡有一堆選單面板：背包、任務日誌、情報、設定、鍵位設定。它們有一組共同的行為：

- 打開時要**鎖住玩家移動**（不然玩家會邊看背包邊走路）
- 關閉時要解鎖
- 開關要有音效
- **同時只能開一個** — 開背包時如果任務面板還開著，兩個會疊在一起
- 對話進行中不能開
- 按 Esc 要能關掉，沒開任何面板時按 Esc 要打開設定

如果每個面板各自實作這些，五個面板就是五份幾乎一樣的程式碼，而且一定會有某個面板漏掉某條規則。

## 三層設計

**第一層：`IMenuPanel` 介面** — 只規定三件事：現在開著嗎、打開、強制關閉。

「介面」(interface) 可以想成一份契約：任何東西只要答應做到這三件事，就能被統一管理，管理者不需要知道它到底是背包還是設定。

**第二層：`MenuPanelBase` 抽象基底類別** — 把上面那組共同行為實作一次。所有面板繼承它，就自動具備全部規則。

子類別只需要處理自己獨有的事情：背包要重建道具格子、任務面板要重建任務清單、設定面板要同步音量滑桿。這些透過覆寫 `OnOpened()` / `OnClosed()` 兩個掛勾接進開關流程即可。

**第三層：`UIPanelManager`** — 管互斥和 Esc。

互斥的機制很簡單：任何面板要打開時先通知它，它就把上一個開著的關掉。

## 一個容易忽略的細節：兩種「關閉」

`MenuPanelBase` 有兩個關閉方法，差別很微妙但很重要：

- **`Close()`** — 玩家自己按鍵關的。關完之後要**通知管理者**「現在沒有面板開著了」
- **`ForceClose()`** — 管理者叫它關的（因為玩家開了別的面板）。**不能再通知管理者**，因為就是它叫的

如果混用，會出現一個難查的 bug：玩家開背包 → 管理者關掉任務面板 → 任務面板回頭通知「我關了」→ 管理者以為現在沒面板開著 → 但背包其實開著 → 下次按 Esc 沒反應。

**這是「呼叫方向」造成的問題**：同一個動作，從上往下呼叫和從下往上呼叫，善後方式不一樣。

## 「對話中不能開選單」為什麼要擋

對話系統和選單系統**都會鎖玩家移動**。如果對話進行中還能開背包，兩邊的鎖會打架：

玩家在對話中開背包（鎖住）→ 關背包（解鎖）→ **但對話還沒結束**，玩家卻可以走了。

擋在 `MenuPanelBase.Open()` 裡一次解決，所有面板都受保護。

## TabGroup：一個元件，兩種用法

後來要把背包、任務、情報做成**可以用滑鼠切換的分頁**，另外設定面板裡也要有「音量 / 鍵位」的子分頁。

這兩個需求看起來像兩個不同的東西：

| | 資訊視窗分頁 | 設定的子分頁 |
|---|---|---|
| 每頁是什麼 | 獨立的 `MenuPanelBase` 面板 | 只是一個顯示區塊 |
| 切換方式 | 關掉舊的、開啟新的 | 單純顯示/隱藏 |
| 可以全部關掉嗎 | 可以（整個視窗關閉） | 不行，永遠有一頁選中 |
| 有快捷鍵嗎 | 有（Tab / Q / I） | 沒有 |

但它們的骨架完全一樣：一排按鈕、點了切換、選中的那個要highlight。所以做成**同一個元件、用一個開關切換行為**（`alwaysHasSelection`）：

- 關 = 視窗模式，每頁是面板，可以全部關閉，吃快捷鍵
- 開 = 子分頁模式，每頁是顯示區塊，永遠有一頁選中

省下寫兩個幾乎一樣的元件。

## 一個同步問題

視窗模式下，面板可能**被 Esc 從外面關掉**——這時分頁列不知道，還亮著「背包」那一格。

修法是在 `Update()` 裡持續比對：如果目前選中的那一頁其實已經關了，就把分頁列也收起來。這種「輪詢同步」不是最優雅的做法（理想上應該用事件通知），但在這個規模下最單純可靠，也不會有漏接事件的風險。

## 踩過的坑：加了分頁列之後版面爆掉

分頁列是一排橫向按鈕，加在面板頂端。加上去之後，面板內容超出下緣、跟分頁列重疊。

第一次的修法是**把內容往下移 26 像素**——結果底部反而超出 6 像素。

原因是那些內容元件是**垂直拉伸**的（上下都貼齊父容器），對這種元件來說「往下移」不會讓它變短，只會讓上下兩端一起往下跑。正確做法是**同時減少高度**：往下移 25、高度減 90。

還有一個連帶的錯誤：我當時假設某個按鈕的錨點在中心，實際上它在頂端。錨點決定了「座標值代表什麼意思」，猜錯就會把按鈕推到面板外面去。

**教訓**：UI 版面的除錯不能靠肉眼估，要去讀元件的錨點和拉伸設定，那決定了每個數值的實際意義。

## 報告可以這樣講

這章適合講「**繼承與介面在實務上解決什麼問題**」，是很標準的物件導向教學案例，但有真實的專案脈絡撐著，比課本例子有說服力。

`TabGroup` 一個元件兩種用法那段，可以講「**在抽象化和分開實作之間怎麼取捨**」——判準是骨架有沒有真的一樣，如果只是「看起來像」就硬合併，反而會讓程式碼變複雜。

那個「兩種關閉」的細節適合當一個小驚喜：同一個功能為什麼要有兩個方法。

# 系統 6 — 通知與飄字

## 這個系統在解決什麼

遊戲要告訴玩家「剛剛發生了什麼」。但不同的事情，重要程度天差地遠：

- **接到新任務、任務完成、獲得情報** → 重要，玩家需要知道，而且可能要去看詳情
- **撿到一株甜菜** → 不重要，知道一下就好，不該打斷玩家

一開始只有一套機制（任務通知），撿東西完全沒有回饋。後來加飄字時的第一直覺是「複用同一套」——但很快就發現不對。

## 兩條管道，職責分明

| | `NotificationToast` | `FloatingText` |
|---|---|---|
| 位置 | 畫面左上角固定位置 | 物品原地冒出 |
| 外觀 | 有深色底框 | 只有文字，沒有背景 |
| 行為 | 停留 4 秒 | 上飄並淡出，1.2 秒 |
| 多筆同時 | **排隊**，一則一則播完 | 直接疊，往上錯開 |
| 用途 | 系統訊息（任務、情報） | 現場輕量回饋（撿道具） |

關鍵差異在**「多筆同時發生怎麼辦」**：系統訊息不能互相蓋掉（玩家可能漏看重要資訊），所以要排隊；現場回饋則相反，連撿三樣東西時排隊反而奇怪，直接疊著顯示才符合直覺。

## 通知 toast 的排隊機制

一開始沒有排隊，直接覆蓋文字。問題出在愛拉的對話：同一個選項**同時**接下任務又解鎖情報，兩個事件在同一瞬間觸發，玩家只看得到後面那則。

改成佇列 (Queue)：事件進來就排隊，沒有正在顯示就馬上播，顯示時間到（或玩家提前按鍵關掉）就自動接著播下一則。

### 「按 Q 看詳情」的提示怎麼做才通用

接到任務時通知會提示「按 Q 了解任務詳情」。獲得情報時要提示「按 I 了解情報詳情」。

第一版是寫死的。後來要加鍵位自訂功能（系統 7），寫死的按鍵字母就會跟玩家改過的鍵位對不上。

改成每則通知自己帶三個資訊：**要提示哪個動作、提示文字寫什麼、按下去要不要提早關掉**。按鍵字母透過鍵位系統查詢，玩家改了鍵位會自動跟著換。

還有一個小分工：按下 Q 時「關掉通知」和「打開任務面板」是**兩個系統各自監聽同一個按鍵**，通知系統不去呼叫面板。這樣避免同一幀互相搶著開關造成閃爍。

### 音效的簡化

第一版每種通知各有一個音效欄位，結果「接任務」和「獲得情報」都手動設成同一顆音效，純粹是重複設定。

改成**預設音效 + 例外**：大部分通知吃預設值，只有「任務完成」需要不同的音效才特別指定。以後新增任何通知，不特別設定就自動有音效。

## 飄字的實作重點

**訂閱背包事件，而不是逐個來源接。** 飄字系統監聽的是「背包成功加入道具」這個事件，所以不管是從地上撿的、還是任務獎勵發的，都會有一致的回饋。如果改成在每個給道具的地方各自呼叫一次，一定會有地方漏掉。

**文字不能掛在物品身上。** 因為拾取物在被撿走的當下就把自己銷毀了。所以必須由管理者生成飄字，並在生成的當下把座標複製一份。

**每一幀都要重算螢幕座標。** 飄字是 UI（畫在螢幕上），但它要跟著世界裡的某個位置。如果只在生成時換算一次，相機一移動文字就會黏在畫面上不動。

**沒有底色就一定要描邊。** 白字在亮綠色草地上會糊掉。加了深色描邊之後才讀得清楚。

**要留出高度。** 第一版的文字直接壓在角色身上，看起來像貼紙。加了一個往上的初始偏移才解決。

**畫在其他 UI 底下。** 飄字的容器放在 UI 畫布的最底層，這樣它不會蓋住對話框或選單。

## 怎麼驗證一個 1.2 秒的動畫

這是個實際的方法論問題：動畫只有 1.2 秒，而我每次對 Unity 下指令來回要好幾秒——**截圖一定拍不到**。

用了兩個手法：

1. **看外觀** → 暫時把持續時間改成 60 秒，撿完再截圖，確認完改回去
2. **看動態** → 連續兩次讀取「透明度」和「螢幕 Y 座標」，看數值有沒有在變（實測透明度 0.533 → 0.400、Y 座標 606 → 613）

疊字功能則是連撿三樣，量出螢幕 Y 是 518 / 547 / 576，等距不重疊。

## 報告可以這樣講

這章的核心是**「看起來很像的兩個需求，為什麼不該用同一套機制」**。判準不是外觀，而是「多筆同時發生時該怎麼辦」——這個問題的答案完全相反，所以必須分成兩套。

那個 1.2 秒動畫的驗證方法也值得一提：**當觀測手段比被觀測的現象還慢時，要改變觀測方式，而不是放棄驗證**。

# 系統 7 — 鍵位設定

## 這個系統在解決什麼

原本每個腳本各自寫死按鍵：對話系統寫 `Input.GetKeyDown(KeyCode.F)`、背包寫 `KeyCode.Tab`、任務寫 `KeyCode.Q`。

要做「讓玩家自訂按鍵」的話，得把散在十幾個地方的判斷全部改掉。而且以後每加一個新功能，都可能有人不小心又寫死一次。

## 設計：先做查詢層，之後才做 UI

`KeyBindings` 是一個純靜態類別（不掛在場景上的工具箱）。它做三件事：

1. 定義有哪些「動作」（移動四向、互動、衝刺、開背包、開任務、開情報，共 9 個）
2. 記錄每個動作目前綁哪顆鍵
3. 提供 `KeyBindings.GetKeyDown(動作)` 取代原本的 `Input.GetKeyDown(按鍵)`

值得一提的是**這一層是先做的，UI 是後來才補的**。當時還沒有鍵位設定畫面，但先把所有腳本改成透過這層查詢，之後做 UI 時就完全不用回頭改任何一支腳本。

## 存在哪裡：PlayerPrefs，不是存檔

鍵位設定用 `PlayerPrefs`（Unity 提供的簡易鍵值儲存）存，**不放進遊戲存檔**。

理由是：鍵位是**玩家這台裝置的偏好**，跟遊戲進度無關。玩家不會希望「讀取存檔 1 的時候按鍵是 WASD，讀取存檔 2 就變成方向鍵」。音量設定也是同樣的道理，走同一套邏輯。

這條分界線是：
- **裝置偏好**（音量、鍵位、視窗大小）→ PlayerPrefs，全域共用
- **遊戲進度**（任務、背包、位置）→ 存檔 JSON，每個槽獨立

## 按鍵衝突：自動對調，而不是報錯

玩家想把「互動」改成 W，但 W 已經被「向上移動」佔用了。

常見的處理有三種：
1. 拒絕，跳出「這顆鍵已被使用」
2. 允許，兩個動作都綁 W（會同時觸發，通常是壞的）
3. **自動對調**：互動變成 W，向上移動變成原本互動的 F

專案選第 3 種。理由是：**它永遠不會產生「某個動作沒有鍵可按」的狀態**，也不用跟玩家解釋錯誤。玩家只要看到兩行同時變了，直覺就懂發生什麼事。

`Rebind()` 會回傳「被對調掉的是哪個動作」，方便 UI 提示玩家。

## 開發中撞到的規格問題

原本的規劃有 11 個動作，其中包含「對話選項上移 / 下移」。

做到一半發現：**「選項上移」和「向上移動」預設都是 W**——而剛剛設計的自動對調機制，會把這兩個當成衝突處理，一改就互相對調，整個亂掉。

想了一下，這兩個動作本來就沒有分開的必要：對話中選選項，用移動鍵上下選是最直覺的。所以**直接刪掉那兩個動作**，讓對話選項沿用移動鍵，從 11 個減成 9 個。

這是規格上的縮減，當時有明確回報給你確認過。

## 兩個刻意不做成可改的按鍵

**Esc** — 幾乎所有遊戲都用它當「返回/開選單」，玩家的肌肉記憶就是這樣，改了反而困惑。

**方向鍵** — 移動的四個鍵可以改，但方向鍵永遠可用，當作保底。這樣玩家就算把 WASD 改到奇怪的地方，也不會卡住走不動。

## 一個跨系統的互動

改鍵位時，畫面會進入「等你按下新鍵」的狀態。這時按 Esc 的意思應該是**取消改鍵**，而不是關閉整個設定視窗。

但 Esc 是由 `UIPanelManager` 統一處理的（系統 5）。所以那邊加了一個判斷：**先問鍵位設定「你現在是不是在等玩家按鍵？」**，是的話就不動作，把 Esc 讓給它處理。

**這是很典型的跨系統協調問題**：一個全域的快捷鍵，在特定模式下要有不同的意思。做法是讓全域處理者「先問過可能有意見的人」，而不是讓每個模式各自去搶。

## 報告可以這樣講

三個賣點：

1. **抽象層要先做**。這個系統示範了「先做查詢層、之後才做 UI」的價值——UI 做完時完全不用回頭改任何腳本。
2. **衝突處理的三選一**。自動對調 vs 拒絕 vs 允許重複，是很好的設計選擇題，可以讓聽眾先猜再公布。
3. **規格中途縮減**。11 個動作減成 9 個，是因為做到一半才發現設計本身有矛盾。這是很真實的開發經驗——**規格不是想好就不會變的**。

# 系統 8 — 相機與地圖邊界

## 這個系統在解決什麼

兩個相關的問題：

1. **相機會拍到地圖外面**——玩家走到村莊邊緣，畫面下半部是黑的（沒有東西的虛空）
2. **玩家可以走出地圖**——一直往西走，會離開所有地形，走進純黑的空間

## 設計原則：不要單純加空氣牆

你當時明確說「不想要單純加空氣牆」。這個要求指出了問題的本質：

**關鍵不在有沒有碰撞牆，而在「玩家看得到開闊地卻走不過去」才出戲。**

所以做法是：**先用視覺講清楚這裡過不去，碰撞牆藏在後面**。玩家永遠不會意識到那道牆存在，因為他從來沒想過要往那邊走。

## 動手前的地形測量

在放任何東西之前，先量了一次地圖，結果直接改變了做法：

| 測量項目 | 結果 |
|---|---|
| 草地鋪設範圍 | 268 × 230 格 |
| **實際有裝飾的範圍** | 只有約 130 × 110 格 |
| 河流（有碰撞） | 從 y=−49 到 y=54 **連續無缺口、沒有橋** |
| 河的南北端 | 會收成尖端，外側是唯一能繞過去的破口 |
| 現有道路 | 全部止於地圖內部，**沒有任何一條通到邊緣** |

最關鍵的發現是**河流本身就是一道天然的東界**——它沒有橋、沒有缺口，玩家本來就過不去。所以**東面完全不用做**，只要在南北兩個尖端外側塞兩個小塞子，防止玩家繞過去。

這個發現讓需要圍的長度**從 484 格降到約 271 格**，工作量少了將近一半。

**教訓**：動手之前先量，量出來的事實可能直接讓一半的工作消失。

## 實作內容

全部放在村莊場景的 `[Boundary]` 群組底下，分三塊：

**視覺層 — 230 棵邊界樹**
用現有的樹木素材，外排放大樹擋視線、內排混小樹做層次，位置帶亂數擾動避免整排太整齊。西面、北面、南面各鋪一排，河的南端塞一個。

**碰撞層 — 5 道碰撞牆**
藏在樹後面。玩家視覺上早就被樹擋住了，根本走不到牆的位置。

**出口 — 村口**
南面刻意留一個缺口（村莊的對外道路正好在那裡，亞爾就坐在旁邊），放一道柵欄 + 一個可查看的區域，文字提到南方通往「眠雪鎮」。這樣邊界就不只是「牆」，而是「這裡有路，只是現在不能去」——給了世界觀延伸的空間。

## 相機夾制

相機和玩家都住在常駐場景，換地圖時不會重載，**所以邊界值必須由「當下載入的那個場景」自己帶進來**。

做法是一個 `CameraBounds` 元件，每個場景自己放一個，宣告相機可以拍到的範圍。它在啟用時把自己登記成「目前生效的邊界」，場景被卸載時元件跟著消失，登記自動失效。

### 一個數學地雷

夾制的公式是「相機中心不能超過 邊界 ± 半個畫面」。但如果**地圖比畫面還小**呢？

這時候「下限」會**大於**「上限」——直接丟給夾制函式會得到亂七八糟的值，畫面會抖動或跳到奇怪的位置。

四間室內場景全部都比畫面小（房間 11×11 或 19×12，畫面是 24.3×14），所以這不是理論問題，是一定會踩到的。

正確的行為是：**這種情況要把相機釘在地圖中心**，讓兩側均勻露出外面。實際效果是黑邊變成對稱靜止的細框，看起來像刻意的取景，而不是破圖。

## 怎麼驗證「玩家真的走不出去」

這是這個系統最值得講的部分。

**錯誤的驗證方式**是沿著牆掃一遍，看有沒有洞。這只能證明「牆沒破」，**證明不了「沒有繞路」**——玩家可能從某個意想不到的角度繞過去。

正確的做法是**洪水填充演算法**（Flood Fill，用 BFS 廣度優先搜尋實作）：

1. 把整個區域切成 1 格 × 1 格的網格
2. 對每一格做一次碰撞偵測，標記哪些格子被擋住
3. **從村子中央的路上出發**，往四個方向擴散，能走到的格子就繼續往外擴散
4. 擴散停止後，看看「玩家實際能到達的所有格子」的範圍有多大

實測結果：可達範圍是 **x −59～40, y −54～55**。

這個數字證明了兩件事：西南北三面都被擋在預期的位置；而且**東岸雖然地形一直延伸到 x=71，玩家卻走不到**——證明河流加上兩個塞子真的封住了。

**這個方法的價值在於**：它不是「檢查我做的牆對不對」，而是「**直接模擬玩家會怎麼走**」。前者只能驗證你想到的地方，後者連你沒想到的破口都會找出來。

## 報告可以這樣講

這章有三個層次，都很好講：

1. **設計原則**：「不要空氣牆」這個要求怎麼轉譯成「視覺先講清楚，碰撞藏後面」
2. **先量再做**：河流的發現讓工作量減半，是「動手前先調查」的完美案例
3. **驗證方法**：洪水填充。這是整份報告裡最能展現「工程化思維」的一段——**用演算法驗證關卡設計，而不是靠人工試走**

第 3 點適合當這章的高潮，可以畫一張示意圖：一張是「掃牆面」（只能看到牆），一張是「洪水填充」（看到玩家真正能到達的區域）。

# 系統 9 — 中文字型工程

這是整個專案偵錯難度最高的問題，總共有**三層獨立的原因疊在一起**，每一層都得單獨解決。

## 症狀

對話框裡的中文字，**有些明顯比較大**，而且**有些上下位置歪掉**，看起來像排版壞掉。

## 背景知識：Dynamic 字型與 fallback

專案用的文字元件叫 TextMeshPro。它處理中文的方式是「**動態字型**」(Dynamic)：不預先把幾萬個中文字都畫好（那會非常大），而是**第一次用到某個字時，才即時從字型檔畫進一張圖集**。

另外它有「**備援字型**」(fallback) 機制：主字型如果沒有某個字，就去備援字型找。

專案的設定是：主字型 `Silver`，備援 `Cubic`。

## 第一層：圖集裡卡了舊快取

`Silver` 的取樣設定在專案歷史上被改過。改之前就已經畫進圖集的字（例如「撿」「起」），用的還是舊尺寸。

修法是把整個字元表清空，強迫全部重新產生。

**但這層修完，只解決了「Silver 自己內部」的不一致**，備援字型的問題完全沒動到。

## 第二層：備援字型天生就比較大

真正的主因在這裡。

`Silver` 這個字型檔的字符集很小，只涵蓋部分常用字。**只要用到 Silver 沒有的字，就會自動 fallback 到 Cubic**——而 Cubic 的字在字型設計上就**比 Silver 高快 6 成**。

量化數據（同樣的取樣大小下）：

| 字型 | 字高中位數 |
|---|---|
| Silver | 52.1 |
| Cubic | 82.5 |

而且缺字的機率很高：「這」「們」「東」「西」「喜」「歡」這種常用字都會中。所以幾乎任何一段稍長的對話都會踩到。

### 花了很多輪才找到正確的調整欄位

TextMeshPro 有好幾個看起來能調大小的欄位，但**大部分都沒有淨效果**：

改「字型大小基準」(`pointSize`)、「上緣線」、「下緣線」、「行高」都試過——**看數字以為修好了，實際截圖還是錯**。

原因是這些欄位有連鎖效應：改基準值會讓字的原始高度跟著等比例縮小，但顯示時的縮放倍率同時等比例變大，**兩者相乘直接抵銷**。

唯一真正有效的是一個叫 `faceInfo.scale` 的獨立乘數。它不會被抵銷。要讓備援字型看起來跟主字型一樣大，公式是：

```
scale = 主字型字高中位數 ÷ 備援字型字高中位數
      = 52.1 ÷ 82.5
      ≈ 0.631
```

### 驗證這種修改的正確方法

改完之後不能用「已經顯示過的字」去測——那些字的資料已經在快取裡，容易搞混「這次到底有沒有重新計算」。

保險做法是用**這個執行階段完全沒出現過的全新字**（當時用了「貓咪汪」）去測，直接讀取「這個字實際用的是哪個字型、實際的縮放倍率是多少」這兩個真正的事實來源。

**最終驗證**：把專案裡所有對話、任務、道具的文字全部餵進對話框強制產生一次，對每個字計算真正的視覺高度，排序後看分布。結果是全專案 371 個不重複字元，只剩標點符號合理地比較矮，中文字全部落在中位數 ±18% 以內。

## 第三層：垂直位置對不齊

大小修好之後，還剩「同一行有些字上下位置偏掉」。這是**跟大小完全無關的另一個問題**。

真因是兩套字型「字框相對於基準線的位置」天生不同：

- **Silver**：漢字、數字、大寫字母的字框底部**剛好坐在基準線上**
- **Cubic**：漢字的字框**整個往下垂 15 個單位**

換算成畫面上大約差 2.5 個單位，是字級的 10%——看得很明顯。

### TextMeshPro 沒有「備援字型垂直偏移」這種設定

試過調「基準線」欄位，**實測完全沒作用**（量出來的座標一模一樣）。縮放欄位只能縮放不能平移。

唯一有效的是直接改每個字自己的「上緣間距」(`horizontalBearingY`)——這個數值決定了每個字畫多高。

於是寫了一支工具 `FontBaselineAligner`，規則是「**把字框底部對齊基準線**」。

### 為什麼選這個規則

因為它是**冪等**的——跑第二次會改動 0 個字。

替代方案是「統一往上位移 15」，但那個沒辦法判斷某個字是否已經位移過，重複執行會不斷疊加，最後全部飛到天上去。冪等這個性質讓工具可以安全地重複執行、跨開發階段執行，不用擔心狀態。

### 為什麼需要常駐執行

因為 Cubic 是動態字型——遇到沒看過的字才即時補進來，**補進來的是原始沒對齊的數值**。

所以這個工具做成常駐元件，持續比對字元數量，數量一變多就重修一次。實測：塞入全新的字「鑫淼犇」，當幀量到偏移 −15，**下一幀就變成 0**。代價是全新字元第一幀會有一格的錯位，實務上看不出來。

## 第四層：編輯器裡正常，打包出來又壞了

這一層最陰險。編輯器裡完全正常，**但打包成執行檔之後，字又高低不一**。

真因是 TextMeshPro 的動態字型有一個叫 `ClearDynamicDataOnBuild` 的屬性，**預設是開啟**——建置時會把整個字元表清空，理由是「動態產生的資料不需要打包進去」。

但我們手動改好的對齊數值**就存在那個字元表裡**，全部被丟掉了。執行時再從字型檔重新產生，變回原始沒對齊的數值。

徵兆很好認：**建置完回到編輯器，會發現 Cubic 的字元數從 180 掉到 19**。

那支常駐的對齊工具確實還在跑，但它只能「事後補救」——每個字都要先用錯的數值產生一次才會被修，實務上救不回來。

### 修法（兩件一起做才完整）

1. **把兩個字型的 `ClearDynamicDataOnBuild` 關掉**，資料才會跟著打包
2. **事先把全遊戲會用到的字烘進字型資產**，不要靠執行期動態產生

第 2 步的做法是：掃描所有對話、任務、道具、情報的字串，加上程式裡寫死的 UI 文字、全部 ASCII、常用中文標點，先餵給主字型，**再把主字型缺的那些餵給備援字型**（跟執行期 fallback 的順序一致）。

結果：591 個不重複字元 → Silver 218 個、Cubic 375 個（4 張圖集），零缺字。最後再跑一次對齊工具。

### 驗證方式

建置完之後回編輯器看字元數——**還是 375 就代表資料保住了**（修之前這裡會變成 19）。

最近一次建置（含這次的所有改動）實測：Silver 218 → **218**、Cubic 388 → **388**，未對齊字元 **0**。

## 一個持續性的維護負擔

**以後新增對話或道具文字時，如果用到全新的字，要重跑一次「烘字 + 對齊」流程**，否則打包版那些字會是沒對齊的。

這就是為什麼系統 2 那個台詞搬移，是「逐字沿用既有句子」而不是重寫——**零新字元就不用重跑這套流程**。

## 報告可以這樣講

這是整份報告最有料的一章，建議放最重的篇幅。它的價值不在「修好了一個 bug」，而在**它示範了系統性排查長什麼樣子**：

- **一個症狀可能有多個獨立成因**。修完第一層看起來有改善，但其實根本原因還沒碰到。如果當時就停手，問題會反覆出現。
- **「看數字以為修好了」是真的會發生的**。調基準值那條路試了兩輪才發現被抵銷——教訓是要驗證到最終的視覺結果，不能只看中間變數。
- **冪等性是個實用的設計判準**。同樣能達成目的的兩個規則，選可以安全重複執行的那個。
- **編輯器裡對 ≠ 打包後對**。這是遊戲開發最容易翻車的地方，而且測試越充分越容易產生虛假的信心。

那個「字元數從 180 掉到 19」的徵兆，是很好的偵探故事素材——一個具體、可觀測的數字，直指真因。

# 系統 10 — 2D 渲染

## 這個系統在解決什麼

這是個 2D 遊戲，但要有「立體感」——玩家走到樹的**前面**時要遮住樹，走到樹的**後面**時要被樹遮住。

2D 遊戲裡沒有深度的概念，所有東西都畫在同一個平面上，畫的順序由一個「排序序號」決定，序號大的畫在上面。如果序號是固定的，那玩家要嘛永遠在樹前面、要嘛永遠在樹後面，兩種都很怪。

## 解法：用 Y 座標決定畫的順序

規則很簡單：**畫面上越低的東西，畫在越前面**。

因為在俯視角的 2D 遊戲裡，「比較低」在視覺上就代表「比較靠近鏡頭」。玩家走到樹的下方（Y 比較小），就會蓋住樹；走到樹的上方，就被樹蓋住。

實作就是一行公式：

```
排序序號 = 四捨五入(−(物件的 Y 座標 + 微調值) × 100)
```

乘 100 是為了保留小數精度（不然同一格內的物件會分不出前後），取負號是因為 Y 越小要越前面。

那個「微調值」是給美術用的：有些物件的視覺重心跟它的座標點不一致（例如一棵樹的座標點在樹根，但視覺上樹冠更該當基準），可以逐物件微調。

## 一個容易忽略的細節：編輯器裡也要跑

第一版只在遊戲執行時計算排序。結果**在編輯器的場景視窗裡看，所有物件的排序都停在預設值**——樹木、草叢密集重疊的地方會出現排序錯亂、硬切邊。

這對開發流程影響很大：你在編輯器裡擺場景，看到的畫面跟實際玩起來不一樣，等於**沒辦法用眼睛確認擺得對不對**。

修法是加一個標記，讓這段計算在編輯器裡也持續執行。

**這個坑的通則是**：跟視覺呈現有關的邏輯，最好在編輯器裡也生效，否則會破壞「所見即所得」的工作流程。

## 相關：拾取物的互動偵測

嚴格說這屬於玩家控制，但跟 2D 的空間判斷有關，一併記在這裡。

原本的互動偵測是**射線**：從玩家腳下往面朝的方向射一條線，打到什麼就是互動目標。

問題是：**如果玩家踩在物品正上方**（可穿越的拾取物，玩家可以走進去），射線的起點已經在物品的碰撞範圍外側了，反而打不到——明明就站在上面，卻按不到。

改成**範圍偵測**：以玩家前方一小段距離為圓心畫一個圓，抓範圍內所有物件，再挑一個最合適的。

挑選規則是「**面朝方向優先，角度相同才比距離**」——這樣玩家面向哪邊就優先跟那邊的東西互動，符合直覺。

### 順手修掉的另一個 bug

舊的射線只會回傳**打到的第一個**物件。如果那個剛好是不能互動的（例如田裡還沒成熟的那格），後面即使還有可互動的東西也完全打不到——因為射線根本沒機會檢查第二個。

改成「先抓全部候選、再挑一個」之後，這個限制自然消失。

## 報告可以這樣講

這章最適合當**技術部分的收尾**，因為它短、直觀、而且有很強的視覺效果可以展示（一張玩家在樹前、一張在樹後）。

「一行公式做出假立體感」是很討喜的講法——**用最簡單的規則解決看起來很複雜的問題**。

編輯器裡也要跑那個細節，可以講「工具的正確性也是產品的一部分」。

# 附錄 A — 貫穿全專案的幾個原則

寫完十個系統，回頭看有幾個重複出現的模式：

## 一、執行期狀態 vs 持久化狀態

任何「玩家改變了世界」的事情，都不能只改執行期狀態。這條規則在三個地方出現：

- 場景重載會把採收過的作物變回來（系統 1）
- 存檔要記住撿過什麼、觸發過什麼（系統 4）
- 建置會把字型的動態資料清空（系統 9）

三個看起來完全無關的問題，本質是同一件事：**暫時的資料會在某個時間點被丟掉，你必須知道那個時間點在哪**。

## 二、安靜失敗比崩潰更危險

專案裡有好幾個 bug 的共同特徵是「不會報錯」：

- 找不到玩家角色（因為它是關閉狀態）→ 安靜跳過定位
- 場景名稱打錯 → 回傳 null，然後崩在後面
- 存檔的 ID 在資料庫裡找不到 → 那筆進度安靜消失

後來的處理方式是**主動加警告**。例如任務階段索引設錯不會真的壞掉（程式會安全地夾住範圍），但會安靜地顯示錯的目標文字——所以加了一行警告，明確告訴開發者是設定檔的問題。

**判準是**：如果一個錯誤會導致「行為不對但沒有任何線索」，就一定要加提示。

## 三、抽象層要在需要之前先做

鍵位系統是最好的例子：查詢層先做，當時根本還沒有設定畫面。等到真的要做 UI 時，完全不用回頭改任何腳本。

反例是通知系統的「按 Q 看詳情」——第一版把按鍵寫死，等到鍵位可以自訂時就得回頭改。

## 四、驗證方式要跟被驗證的東西匹配

專案裡用過幾種不同的驗證手法，每一種都是為了特定的觀測難題設計的：

| 要驗證什麼 | 難點 | 用的方法 |
|---|---|---|
| 玩家走不出地圖 | 掃牆面證明不了「沒繞路」 | 洪水填充，直接模擬玩家能走到哪 |
| 1.2 秒的飄字動畫 | 觀測比現象還慢 | 暫時把時間拉長到 60 秒截圖 |
| 字型大小改對了 | 快取會混淆判斷 | 用全新的字測，讀真正的事實來源 |
| 打包後字型有沒有壞 | 編輯器裡看不出來 | 建置完回頭看字元數量 |
| UI 有沒有重疊 | 肉眼估不準 | 讀元件的實際角落座標計算 |

共通點是：**不要用「看起來對」當作驗證**。

## 五、內容和架構的接縫最容易出問題

賽勒那個「要講兩次話」的問題，在技術上完全正確——每個函式都做了它該做的事。但玩家的體感是壞的。

這種問題只有實際玩過才抓得到，而且修法通常橫跨兩邊：改架構（自動接續）**加上**改內容（把重複的台詞搬走）。
